## Cause racine transverse

Presque tout l'accès données passe par le client **service-role** (`createSupabaseAdmin`), qui **contourne la RLS**. La sécurité repose donc entièrement sur les contrôles applicatifs de chaque route — or plusieurs routes n'en ont aucun, et plusieurs surfaces font confiance à des identifiants fournis par le client (`user_id`, `plan`, `id` de projet). **Corriger ce pattern** (dériver l'identité de la session, vérifier la propriété, réserver le service-role au travail serveur vraiment de confiance) ferme la majorité du rapport.

## CRITIQUE — 🔶 à décider (liés à la posture démo, ne PAS corriger sans arbitrage)

Ces points cassent la monétisation, mais sont entremêlés avec le mode démo assumé (Stripe factice, `PAYWALL_DISABLED=true`). **À traiter impérativement avant toute mise en prod payante.**

### C1 — Bypass paiement : `/billing/success` crédite un `user_id` arbitraire
`app/billing/success/page.tsx` applique l'achat sur un **GET non authentifié** : `?type=credits_volume&user_id=<uuid>` crédite 40 crédits à n'importe qui, rejouable à l'infini (idempotence nulle), y compris le compte d'un tiers. **Fix cible** : n'appliquer crédits/plan **que** dans un webhook Stripe signé, idempotent sur l'event id.

### C2 — Élévation de privilège : le plan vient du client à l'inscription
`/auth?tab=signup&plan=pro` → `signUp` écrit `plan:"pro"` dans `profiles`. Conséquence : générations illimitées gratuites (`checkAndConsumeCredit` renvoie `allowed:true` pour expert/pro) + accès aux routes `/api/pro/*`. **Fix cible** : ignorer tout `plan` client ; le plan n'est posé que par le webhook de paiement.

### C3 — Stripe entièrement factice
`create-checkout-session` renvoie une session `fake_…` et redirige vers la page success ; `webhook` est un stub 200 sans vérification de signature. **Fix cible** : `stripe.webhooks.constructEvent`, rejet sur échec, mapping prix→montant côté serveur.

### C4 — IDOR généralisé sur `/api/projects/:id/*`
`generate, iterate, analyze, constraints, decisions, style, furniture, select-disposition, shopping-status` : aucune ne vérifie que l'appelant possède le projet (et la plupart n'ont aucune auth). Les ids sont des `nanoid()` (fuitent via liens partagés, referer, logs). **Impact** : lecture/écriture cross-tenant (photos de domicile, liste de courses), et dépense Gemini illimitée sur le projet d'autrui via `iterate`/`analyze`. Seule `refresh-shopping` vérifie l'ownership. **Fix cible** : une garde partagée en tête de chaque handler `projects/:id/*` — charger le projet puis exiger `project.userId === session.user.id` **ou** (projets anonymes) correspondance `anon_id` via cookie signé ; renvoyer 404 (pas 403) pour éviter l'oracle d'énumération. *C'est le fix structurel le plus important.*

> **Pourquoi non corrigé maintenant** : ajouter la garde d'ownership casse le flux anonyme de la démo (les projets anonymes n'ont pas de `user.id`). À faire avec toi, en même temps que la décision sur le mode anonyme.

## ÉLEVÉ

### É1 — Endpoints IA non authentifiés · ✅ corrigé
`/api/ai/test` et `/api/prompts/test` étaient hors `/api/admin` (donc hors middleware) et invoquaient Gemini/vision à la demande (dépense illimitée) + fuitaient les prompts résolus. **Supprimés** (zéro caller ; l'équivalent admin `/api/admin/prompts/test` reste).

### É2 — Aucun rate limiting · 🔶 à décider
`upload, generate, iterate, analyze, generate-dispositions` sont sans limite. Un script → facture Gemini + storage. **Fix cible** : rate limiting par IP/utilisateur (Upstash Ratelimit ou Vercel WAF) + compteur anonyme serveur (voir M5). *Nécessite un choix d'infra.*

### É3 — RLS « allow all » + grants `anon` · 🔶 à décider (migration DB)
`0001_initial_schema.sql` laisse `allow all v1 … using(true)` sur `projects, iterations, prompts, prompt_versions, assets, shopping_lists` ; `0005` ajoute `grant … to anon` sur `diy_actions`. Avec l'anon key (publique), requêtes PostgREST directes possibles pour lire/altérer les **prompts propriétaires** et la config `assets`. **Fix cible** : policies scopées `auth.uid()`, révocation des grants `anon` superflus. *Migration à écrire et tester hors prod.*

### É4 — Auth admin fragile · ✅ partiellement corrigé / 🔶 reste
Comparaisons de secrets passées en **temps constant** (`safeEqual`) ✅. Restent 🔶 : mot de passe unique partagé, cookie token statique 7 j, pas de rate limit/lockout sur `/api/admin/login`, aucune auth *dans* les handlers admin (middleware = point unique de défaillance). **Fix cible** : lockout sur login, session signée expirante, idéalement comptes admin + rôle DB, et une vérif d'auth défensive dans chaque route admin.
